    Render

    1. Match styles: each .part gets left: calc(var(--lx) * 1em) and so on Step 7

Step 0

Overview: the HTML is almost empty

In p3_css_typeface.html, the alphabet is just an empty <div id="specimen">. All 26 letters are created by JS after the page loads.

The three files split the work:

  • JS stores the shape data for every letter and turns it into HTML elements and CSS variables.
  • CSS reads those variables to place each part, switches to a second set on hover, and animates the change.
  • HTML provides an empty container and one button.

Result

Step 1

The grid: everything is measured in units

Every letter is drawn on graph paper, with x and y counted in grid units. The guide lines: y = 0 is the top of capitals (cap line), y = 3 is the top of lowercase letters (x-height), y = 8 is the baseline, and y = 10 is where letters like p and y descend to.

Each tile is 9 units wide and 12 units tall. TILE_TOP = -1 means the top row of the tile is y = -1, which leaves one empty row above the cap line.

Result: B on the grid (not centred yet, so the coordinates are easy to read)

Step 2

Shape functions R and C: a few numbers per part

R(x, y, w, h) is a rounded rectangle: (x, y) is its top-left grid cell, and w and h are its width and height. It returns the centre point cx, cy rather than the top-left corner, because rotation later happens around the centre.

radius defaults to "pill", half of the shorter side, so both ends become semicircles. C(x, y, d) is just an R with width and height d and radius d / 2, which makes a circle.

The file also has Q (quarter circle), S (diagonal stroke) and T (triangle). B doesn't use them.

These functions are the toolbox: each call describes one shape and nothing more. No letter exists yet. Shapes are put together into letters in the next step.

Result: one shape at a time. Change the numbers and see what R or C returns

Step 3

B's data: every part has a lowercase and an uppercase version

This is where the shapes from step 2 are put together into a letter. Each letter in GLYPHS is an array of parts, and each part is a pair: [lowercase shape, uppercase shape]. B has three parts: the stem, the upper bowl and the lower bowl.

The stem and the lower bowl are identical in both cases; only the upper bowl differs. In lowercase it sits exactly on top of the lower bowl, so the two circles look like one. In uppercase it moves up 4 units. Going from b to B is just one circle sliding up.

Result: the same parts in both states (colours are translucent, so overlaps look darker)

Step 4

createLetter: building elements in the DOM

First, an important distinction: JS never edits the .html file. The HTML file is just text on disk. When the page opens, the browser reads that text and builds a tree of elements in memory, called the DOM (Document Object Model). The screen always shows the DOM, and JS can change the DOM at any time.

Take B as the example. The HTML file only contains an empty <div id="specimen"> (highlighted in the first code box), so in the DOM that element starts with no children. Then the script runs: getElementById("specimen") finds that element in the DOM, and renderSpecimen calls createLetter("B", …), which builds a button containing a label, a .glyph and three .part spans (stem, upper bowl, lower bowl). Finally container.append(tile) puts the button inside #specimen.

The file still has an empty div; only the DOM has the B tile. Every reload starts from the file again, and JS rebuilds the tile. In a browser, View Page Source shows the file and Inspect shows the live DOM. P3 does the same thing for all 26 letters.

createLetter makes a <button> for each letter (so it can be focused with Tab), puts a .glyph inside it, and adds one .part per shape.

The key point: it never writes left or top directly. Both the lowercase and uppercase values are stored on the element as CSS variables (--l… and --u…), and CSS decides which set to use. Lines 8–9 (the shift) are covered in step 5, and lines 25–26 (setState) in step 6.

Result: the same <main> in the DOM, before and after JS builds B

Step 5

Centring: computing the shift

In the data, B spans x = 3 to 8. The tile is 9 units wide with its centre at 4.5, so drawn as-is the letter sits too far to the right.

extentOf finds the leftmost and rightmost edges of all visible parts, accounting for rotation and skipping hidden parts. centreOf takes the midpoint. shift = half the tile width − glyph centre, and it is added to every part's x. Each case is measured separately, so both states are centred on their own.

Result: tick the box to apply the shift

Step 6

setState: shapes become CSS variables

setState writes a shape as 7 CSS variables, prefixed l for lowercase and u for uppercase. Along the way it:

  • converts x and y from the centre back to the top-left corner, adding the centring shift and the TILE_TOP offset;
  • uses radiusCss to expand the radius into a full border-radius value;
  • sets hidden parts to opacity 0 (B has none; O, Q, R and S do).

On the right are the real values for B's three parts. Highlighted cells differ between the two cases.

Result: the variables written onto B's .part elements

Step 7

CSS: em turns variables into positions

Every size on .part is written as "variable × 1em", so 1em has to equal exactly one grid unit. The font size of .glyph makes that happen: font-size: calc(100cqw / var(--cols)).

cqw is 1% of the container's width. .letter sets container-type: inline-size, which makes it the container, so 100cqw / 9 is one unit. When the tile grows or shrinks, 1em follows and the whole letter scales with it, with no JS involved. Drag the slider to try it.

Result: change the tile width and 1em follows

Step 8

Hover: switch variable sets and let transition fill the gap

By default the .part rule reads the --l… variables (lowercase). When the tile is hovered or focused, a more specific selector makes left, top, width and the rest read the --u… variables (uppercase) instead.

When a property value changes, transition has the browser animate between the two values over 500ms. That is the whole b-to-B animation: the upper bowl's top slides from 5em to 1em. Slow the transition down to see it clearly.

Result: hover, press Tab to focus, or use the button

Step 9

Why the upper bowl slides up from below

In lowercase b the upper bowl isn't missing. It sits at exactly the same position as the lower bowl, so the two circles look like one (you can see the overlap in the coloured demo in step 3).

transition only animates the properties whose values change, from the old value to the new one. For B's upper bowl, only top changes:

Property Lowercase Uppercase Changes?
left3em3emno
top5em1emyes
width / height4em4emno
opacity11no

So the browser animates only top, from 5em to 1em. The circle starts out hidden behind the lower bowl and slides up from there, which is why it seems to come out from below.

Result: watch the upper bowl's top while it switches

Step 10

Finishing touches: the toggle button and other details

  • Toggle button: clicking it adds .is-upper to #specimen. The step 8 selector .specimen.is-upper .part applies the same uppercase rules as hover. aria-pressed tells screen readers whether the button is on.
  • is-ready: the page draws every letter first and only adds is-ready to body, which turns transitions on, two frames later. That way nothing moves when the page opens.
  • Seams: box-shadow: 0 0 0 0.5px on .part grows each part by half a pixel, covering the thin anti-aliasing gaps where two parts meet.
  • Reduced motion: when the system's reduce-motion setting is on, prefers-reduced-motion turns the transitions off.
  • The "maple" heading also uses createLetter, but with standalone = false (a span instead of a button) and a [lowercase width, uppercase width] pair, so the letter spacing changes with the case.

Result: the same toggle button as on the P3 page

Extra

How the 26 tiles line up

This goes beyond B, but it uses the same code. JS decides how many tiles there are and in what order; CSS Grid decides how they are laid out.

How many, and in what order (JS)

  • renderSpecimen loops over Object.keys(GLYPHS). GLYPHS defines 26 letters, A to Z, so the loop runs 26 times and creates 26 button.tile elements.
  • Object.keys returns the keys in the order they were defined, and append always adds to the end, so the order in the DOM is A, B, C … Z.

Lining them up (CSS Grid)

  • display: grid turns the 26 tiles into grid items. The browser fills them in DOM order, left to right and row by row, so no tile needs a position of its own.
  • repeat(auto-fill, minmax(9rem, 1fr)) picks the number of columns. Each column is at least 9rem wide, auto-fill fits in as many columns as possible, and 1fr shares the leftover space equally, so all columns are the same width.
  • max-width: 72rem (1152px) caps the width. Because the page sets box-sizing: border-box, that width includes the 1px left border, leaving 1151px for columns. Eight 9rem columns would need 1152px, so only 7 fit, and each grows to about 164px. A wide screen therefore shows 7 per row: 26 = 7 + 7 + 7 + 5, four rows. A narrower window gets fewer columns, about 2 on a phone.
  • aspect-ratio: 9 / 12: the column sets the width and the height follows, so every tile is the same size and every row lines up.
  • Borders: the grid draws only its top and left edges, and each tile only its right and bottom. Together they make 1px graph paper. If every tile drew all four sides, shared edges would be 2px.

In short: JS decides how many and in what order; CSS Grid decides how many per row, how big, and how they align. When the window is resized, only CSS lays the tiles out again. The JS doesn't run again.

Result: the same grid rules at a third of the size (3rem columns, 24rem max), so it fits this panel

Extra

Why JavaScript? Could CSS alone do the same?

Yes. Everything you see move is already CSS: switching variable sets on hover, the transition, and scaling with em. In this project JS works more like a generator: it turns short shape data into the many numbers CSS needs, and builds the matching HTML.

What JS does, and how you would do it without JS:

What JS does CSS / HTML-only alternative Cost
Builds every element for the 26 tiles and the "maple" heading Write the HTML by hand About 120 .part spans
Turns data like R(3, 0, 1, 8) into 14 CSS variables Write each part's variables by hand, e.g. style="--lx: 2; --ly: 1; …" About 120 × 14 ≈ 1,700 values
Centring: extentOf measures each letter, then the shift is computed Work it out for each letter and bake it into x Change one part and every x in that letter has to be recalculated
Diagonals S(): hypot and atan2 give the length and angle Precompute with a calculator, or use CSS's newer hypot() and atan2() Error-prone by hand; the CSS functions need recent browsers
Per-letter widths for "maple" (--lbox, --ubox) Work out each width by hand Same as above
Toggle button: adds .is-upper and updates aria-pressed A checkbox plus the :has() selector (shown below) Works; the control becomes a checkbox instead of a button, so screen readers announce it differently
is-ready: turns transitions on after the first paint Leave it out Newly inserted elements don't transition anyway, so this is mostly a safeguard

In short: the end result can be identical with only CSS and static HTML. JS is there because it makes the typeface easy to write and change. Each part is one line of data, and the centring, angles and radius values are computed automatically, so changing a shape updates everything derived from it.

A middle ground: a CSS preprocessor such as Sass can generate the same CSS with maps and loops. It does the same job as the JS, just at build time, before the page is published, instead of in the visitor's browser.
